Smart Bumping Logic\n\n### Algorithms Compared\n\n| Algorithm | Description | Pros | Cons |\n|-----------|-------------|------|------|\n| **LRU (Least Recently Used)** | Bump window not accessed longest | Intuitive, matches user mental model | Requires focus tracking |\n| **LRF (Least Recently Focused)** | Similar to LRU but focus-specific | More precise | Same tracking overhead |\n| **Smallest** | Bump window taking least space | Maximizes screen usage | May bump important small windows |\n| **FIFO (First In)** | Bump oldest window in layout | Predictable | Doesn't reflect user intent |\n| **User Preference** | Let user mark \"sticky\" windows | Most control | Requires extra UI |\n\n### Recommended Algorithm: **LRU with Sticky Override**\n\n```\nfunction selectWindowToBump(windows, droppedWindow):\n    # Never bump sticky windows\n    candidates = windows.filter(w => !w.sticky)\n    \n    # Sort by last focus time (oldest first)\n    candidates.sortBy(w => w.lastFocusTime)\n    \n    # Return the least recently used\n    return candidates[0]\n```\n\n**Implementation Notes:**\n- Track `lastFocusTime` whenever a window gains focus\n- Allow users to mark windows as \"sticky\" (won't be bumped)\n- When bumping, animate the window moving to its new location\n\n### Overflow Handling (Dock/Taskbar Pattern)\n\nWindows 11 taskbar behavior provides a model: when at capacity (16+ items), it keeps 3 visible and moves the rest to an overflow menu, maintaining grouping ([Windows 11 Forum](https://www.elevenforum.com/t/taskbar-overflow-odd-behavior.25006/)).\n\n**Recommendation:** When a monitor reaches maximum windows, bumped windows go to:\n1. **Another monitor** (if available and has capacity)\n2. **A \"staging area\"** (minimized but accessible via hotkey)\n3. **Never destroyed** - windows should be recoverable\n\n---\n\n## 3.
